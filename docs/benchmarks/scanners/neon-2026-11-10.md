# Opt-in ARM NEON ASCII run scanning

November 10, 2026. The existing `nitride-core/simd-ascii-runs` feature now selects
16-byte NEON classification on aarch64, alongside the existing x86-64 AVX2 path.
Both ASCII batching features remain off by default. Unsupported targets and
short slices use scalar membership checks; no native CPU build flags are needed.

## Implementation and safety

The scanner reuses the generator-proven ASCII membership table. One table lookup
selects the low-nibble mask and another selects its high-nibble bit. High nibbles
8–15 map to zero, rejecting every non-ASCII byte before UTF-8 decoding. Rejected
lanes retain their 0–15 index; accepted lanes become 255. A minimum reduction
finds the first rejected lane. Complete blocks advance by sixteen bytes; the
existing scalar tail finishes the scan.

Dispatch checks NEON availability and slice length. Each unsafe load is bounded
by a complete sixteen-byte slice or a sixteen-byte initialized table. Neither
ASCII-run replay nor its work/depth/observation/cancellation accounting changes.
Direct tests cover every byte value, singleton/mixed masks, rejection at every
lane, unaligned slices and short tails. Existing lexical and generated-parser
suites cover limits and parser-visible equivalence.

The measured NEON binary's `AsciiRun::scan` assembly contains two `tbl.16b`
instructions and `uminv.16b` in its vector loop. This establishes that the binary
uses the classifier; it does not by itself establish a parser speedup.

## Reproduction

From the repository root, build all variants sequentially with the same toolchain:

```sh
env -u RUSTFLAGS -u CARGO_ENCODED_RUSTFLAGS cargo build --locked --release --manifest-path scripts/compiler-audit/Cargo.toml --target aarch64-apple-darwin --target-dir target/neon-audit/default
env -u RUSTFLAGS -u CARGO_ENCODED_RUSTFLAGS cargo build --locked --release --manifest-path scripts/compiler-audit/Cargo.toml --target aarch64-apple-darwin --target-dir target/neon-audit/scalar --features nitride-core/ascii-runs
env -u RUSTFLAGS -u CARGO_ENCODED_RUSTFLAGS cargo build --locked --release --manifest-path scripts/compiler-audit/Cargo.toml --target aarch64-apple-darwin --target-dir target/neon-audit/neon --features nitride-core/simd-ascii-runs
python3 scripts/benchmark_neon.py --report neon-scanner-run1.json
python3 scripts/benchmark_neon.py --report neon-scanner-run2.json
```

The compiler-audit lockfile was refreshed offline to the current 0.4.0 path
crates, including the authoring library. No registry package versions changed.
The measurement driver consumes existing binaries: the matched commands above
and an idle build/test workload are part of the method. It checks actual core
features and Rust flags from Cargo fingerprints, records binary/source hashes,
and writes new output under ignored `target/reports/`.

Each run uses seven rotating/reversing fresh-process rounds and one untimed
warmup per case/variant. Parse timing excludes input I/O, tree export,
fingerprinting and process launch. Fingerprints, node/diagnostic counts and
logical work must match across all variants, including warmups. Portable release
builds use LTO and the ordinary allocator, with no PGO or affinity pinning.

## Local results

Apple M4 Pro, macOS arm64, rustc 1.99.1 (`58cf8f9c3`, LLVM details in the
[raw evidence](neon-2026-11-10.json)). Two runs retain 336 timed executions and
perform 48 checked warmups, with zero fingerprint, node/diagnostic-count or logical-work
mismatches. Both runs use identical binaries and source hashes. Measurements
were taken from the NEON working tree based on `5b5ae36`: the raw `revision`
field identifies that base, while source hashes identify the measured changes.

Positive percentages mean less parse time than scalar batching; negative values
mean more time. Each time is the median of seven fresh processes.

| Case | Run 1 scalar / NEON (ms) | Run 2 scalar / NEON (ms) | NEON time reduction vs scalar, runs 1 / 2 |
|---|---:|---:|---:|
| 256k-valid | 50.471 / 49.832 | 51.253 / 51.695 | +1.3% / -0.9% |
| 4m-valid | 808.205 / 799.528 | 795.175 / 819.502 | +1.1% / -3.1% |
| 256k-one | 65.779 / 65.468 | 65.197 / 65.818 | +0.5% / -1.0% |
| 256k-dense | 363.448 / 362.106 | 354.065 / 363.898 | +0.4% / -2.8% |
| string-1m | 1.282 / 0.929 | 1.286 / 0.948 | +27.5% / +26.3% |
| comment-1m | 1.036 / 1.003 | 0.987 / 0.976 | +3.1% / +1.1% |
| identifier-64k | 1.431 / 1.447 | 1.360 / 1.366 | -1.1% / -0.4% |
| unicode-escapes | 1.071 / 0.999 | 0.982 / 0.909 | +6.8% / +7.5% |

The long-string case is 1.36–1.38× faster than scalar batching and 3.78× faster
than the default parser in both runs. Unicode/escape-heavy strings improve
6.8–7.5% against scalar batching. These are workload-specific results: mixed
code has no consistent gain, with up to 3.1% more time than scalar batching in
run two. Long identifiers are slightly slower. Neither these small mixed-case
differences nor the comment results isolate a classifier-level effect.

Harness executable sizes are 2,918,640 bytes (default), 2,918,768 (scalar) and
2,918,880 (NEON). These are harness sizes, not shipping CLI sizes. The feature
remains off by default. This is one machine and a bounded workload set, without
PGO, incremental edit timing, peak-memory measurements, a Roslyn comparison or
ARM32 coverage. A larger campaign is needed before changing deployment defaults.

## Verification

- Default workspace: 847 passed, zero failed, three explicitly ignored.
- NEON-enabled core: 150 passed, zero failed; generated lexical/parser suites:
  14 passed. Existing work/depth/observation/repetition cases remain unchanged.
- Nightly AddressSanitizer: all three classifier tests passed on aarch64, including
  direct vector-prefix tests with tails and unaligned inputs.
- All-target/all-feature workspace clippy with warnings denied, formatting and
  all four bootstrap fixed points passed. The wasm32 fallback compiles with
  simd-ascii-runs enabled.
- CI now runs optional scanner core/generated suites on macOS as well as the
  existing Linux quality job. Hosted acceptance of this NEON change is pending;
  no local x86 execution is claimed.

The implementation, tests and driver received independent read-only review.
Historical scanner/compiler evidence was not rewritten or rerun as part of these
new measurements.
