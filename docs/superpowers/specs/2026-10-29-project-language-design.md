# Project language (`.nproj`) design

Status: phases 1–2 implemented (branch `nproj-language`); phase 3 waits for
Nitrogen to read `.nproj`.
Replaces `nitride.json`, `nitrogen.json` and every `languages/*/project.json`
with a Nitride-defined language, the way `docs/catalog-language.md` replaced
`catalog.json`.

## Why

Each language is described in up to three JSON files today:

- root `nitride.json`: name, extensions, grammars, start, `mode`, `catalogs`
  (read by the LSP and the VS Code extension);
- root `nitrogen.json`: name, extensions, grammars, start, `namespace`,
  `sources` (read by the C# Nitrogen toolchain, which lives outside this repo;
  the LSP falls back to it);
- `languages/<x>/project.json`: mode, start, grammars, catalogs (read by
  `nitride prepare` and `nitride-prepare/examples/bootstrap.rs`).

The copies drift. Some drift is intentional — Nitrogen uses
`Dates.Reference.ngr` (generated by `scripts/dates_adapter.py`, adds C#
semantic actions) where Nitride uses `Dates.ngr`; likewise Inference and Calls.
Some is accidental — `Xml` vs `XmlReference`. JSON also has no comments and
errors carry no useful source position.

## Goals

- One `.nproj` file per language folder is the single description of that
  language for Nitride (prepare, CLI, LSP, VS Code) and Nitrogen.
- A root `nitride.nproj` lists the language folders of the workspace.
- The language is defined by a grammar, `languages/project/Project.ngr`, which
  is the shared contract: Nitride parses with a compiled frontend of it,
  Nitrogen generates its parser from the same file.
- Errors carry `.nproj` source spans; the LSP serves `.nproj` like `.ngr` and
  `.ncatalog` (diagnostics, navigation from paths/start rule to the grammar
  file/rule and catalog).
- All three JSON forms are deleted once parity is shown.

## Non-goals

- No change to grammars, catalogs, codegen or the prepared output.
- No glob patterns, variables, conditionals or inheritance between projects.
  Shared grammars are referenced by relative path.
- Implementing the Nitrogen (C#) side is not part of this repo's work; this
  repo provides the grammar and a written resolution contract it must mirror.

## Anti-goals

- Nitride and Nitrogen disagreeing on what a `.nproj` means. Syntax is shared
  by construction (one grammar); resolution is mirrored and pinned by the
  parity fixtures described below.
- Keeping a JSON fallback indefinitely. The transitional `nitrogen.json`
  fallback (below) is removed once Nitrogen reads `.nproj`.

## Syntax

A language file, e.g. `languages/dates/Dates.nproj`:

```ngr
// Dates: calendar arithmetic over day numbers.
language Dates
{
  extensions .dates;
  grammar Dates.ngr;
  start Dates.Program;
  catalog Dates.ncatalog;

  nitrogen
  {
    namespace Nitride.Reference.Dates;
    grammar Dates.Reference.ngr;   // replaces the grammars above for Nitrogen
    source DatesSemantics.cs;
  }
}
```

A language that reuses another folder's grammars, e.g. Rewrites:

```ngr
language Rewrites
{
  extensions .rewrites;
  grammar ../dates/Dates.ngr, Rewrites.ngr;
  start Dates.Program;
  catalog ../dates/Dates.ncatalog;

  nitrogen
  {
    namespace Nitride.Reference.Dates;
    grammar ../dates/Dates.Reference.ngr, Rewrites.ngr;
    source ../dates/DatesSemantics.cs;
  }
}
```

The workspace file, `nitride.nproj` at the repo root:

```ngr
workspace
{
  include languages/portable;
  include languages/power;
  include languages/dates;
  include languages/rewrites;
  // …
}
```

### Rules

- `extensions`, `grammar`, `catalog`, `source` take a comma-separated list and
  may repeat; repeats append in source order. Grammar order is significant and
  is preserved.
- Extensions are written with their leading dot.
- Paths are relative to the directory of the `.nproj` that contains them,
  written with `/`. Paths are unquoted (the grammar defines a path token);
  a quoted form may be added if a real path needs it — builder's call.
- `start` is a qualified rule name, checked against the language's grammars.
- **No `mode`.** A language with at least one `catalog` is typed; one with none
  is syntax-only. This matches all current languages.
- `nitrogen { }` holds only what differs for Nitrogen:
  - `namespace` (required if the block is present);
  - `source` — C# semantic files;
  - `grammar` — if present, *replaces* the outer grammar list for Nitrogen;
    if absent, Nitrogen uses the outer list.
  Name, extensions, start and catalogs are always the outer values.
  Nitride ignores the `nitrogen` block except to validate that its paths exist.
- `include <dir>` in a workspace names a folder holding exactly one `.nproj`
  with a `language` block. Order of includes is the language order (it matters
  where two languages could claim an extension; duplicate extensions are an
  error).
- A `.nproj` contains either one `language` or one `workspace`, never both.
- Comments: `//` and `/* */`, as in `.ngr`.

### Errors (with spans)

Unknown/missing file, duplicate extension across the workspace, start rule not
found in the grammars, `include` folder with zero or several `.nproj`,
`nitrogen` block without `namespace`, unknown keyword, repeated `start`.

## Migration of current data

- One `.nproj` per folder in `languages/` (twelve languages plus `catalog`,
  `grammar` syntax-only projects; `project` itself gets one too).
- `extensions` is optional in a `language` block. `catalog` and `project`
  declare none and are not listed in `nitride.nproj`: their files (`.ncatalog`,
  `.nproj`) stay on the LSP's dedicated paths, and their `.nproj` exists for
  prepare and the bootstrap seed. `grammar` keeps `.nitridegrammar` and stays
  included, as it is in `nitride.json` today. (My call.)
- `languages/signed` stays on the LSP registry's sidecar mechanism and gets no
  `.nproj`. (My call; out of scope.)
- Typed preparation without a catalog is dropped: `nitride prepare` today
  defaults to typed and accepts zero catalogs, which "catalog implies typed"
  cannot express. No language needs it; ad-hoc fixtures in tests and scripts
  are updated. (My call.)
- `Xml` and `XmlReference` become one language, `Xml`, unless the Nitrogen
  side is found to depend on the name `XmlReference` (my call; check when
  mirroring).
- Values come from the existing JSON. Where `nitride.json` and a folder's
  `project.json` disagree, `nitride.json` wins; the builder lists any such case
  in the PR.
- `nitride prepare <file.nproj>` is added. Until phase 3 it also still accepts
  `project.json` unchanged, because the comparison scripts give the same
  `project.json` to both Nitride and Nitrogen.

## Nitride pipeline

- `languages/project/Project.ngr` defines the language. Its compiled frontend
  lives in `nitride-prepare` beside the grammar and catalog seeds, because
  project files must be read before any grammar is loaded (bootstrap).
- `nitride_prepare::project` (name builder's call) parses a `.nproj`, resolves
  paths and names with spans, and produces the existing in-memory project
  structure, so prepare and codegen are unchanged.
- `nitride-lsp/src/manifest.rs` reads `nitride.nproj` and the included
  language files instead of JSON; `.nproj` files join the grammar index so
  navigation crosses into `.ngr` and `.ncatalog`.
- VS Code: activation becomes `workspaceContains:nitride.nproj`. The extension
  no longer parses manifests in TypeScript; it gets the language extensions
  from the server (custom request, e.g. `nitride/languages`) and registers the
  document selector from that, plus `.nproj` itself. (My call: avoids a second
  hand-written parser in TS.)
- Tests and fixtures that write `nitride.json` are moved to `.nproj`.
- **JSON fallback (decided):** until Nitrogen reads `.nproj`, the LSP and the
  VS Code extension keep working in folders that have only `nitrogen.json`
  (e.g. Nitrogen repos outside this one). Lookup order: `nitride.nproj`, then
  `nitrogen.json`. The extension keeps `workspaceContains:nitrogen.json` and
  its TypeScript JSON reader for that case only. The fallback and its tests are
  removed in phase 3, together with `nitrogen.json`.

## Nitrogen mirror

Nitrogen generates its parser from `Project.ngr` and implements the same
resolution: relative paths, `include`, the `nitrogen` block's
replace-grammars rule, catalog-implies-typed. To keep the two sides honest,
this repo ships parity fixtures: for each `.nproj` under `languages/`, a
resolved, normalized JSON snapshot (name, extensions, grammars, start, typed,
catalogs, nitrogen namespace/grammars/sources, with repo-relative paths)
generated by Nitride under `docs/` or a test fixtures folder (builder's call).
Nitrogen's test compares its own resolution against these snapshots.

## Phases

1. `Project.ngr`, the seed frontend, resolution with spans, and a parity test:
   resolving every new `.nproj` reproduces exactly what the three JSON files
   say today (modulo the intended `XmlReference` rename). JSON files stay.
2. Switch `nitride prepare`, the bootstrap example, the CLI and the LSP to
   `.nproj`; LSP serves `.nproj` (diagnostics, navigation). VS Code extension
   switches to the server request. Delete `nitride.json`.
3. Publish the parity snapshots. Delete `nitrogen.json` and every
   `project.json` once the Nitrogen side reads `.nproj`. Until then they stay,
   unread by Nitride, because the C#-comparison scripts
   (`scripts/test_reference.py`, `prepare_parity.py`, `csharp4_reference.py`,
   `csharp_inventory.py`, `test_composition.py`) hand `project.json` to the
   Nitrogen toolchain. The phase-1 parity test keeps them in sync with the
   `.nproj` files. (My call.)
